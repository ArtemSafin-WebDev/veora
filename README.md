# Veora — базовая сборка многостраничного сайта

`/wellness.html` — страница «Оздоровление» здравницы по макетам 1366 и 360. Данные находятся в `src/data/pages/wellness.json`. Первый экран переиспользует `hero` с `variant: "resort"` и `detailVariant: "wellness"`; форма бронирования в hero необязательна. Фотографии и декоративные ресурсы экспортированы из Figma в `public/assets/wellness/`, SVG-знаки подключены через общий спрайт.

Карточки направлений выводятся макросом `wellnessCard(card)` из `src/components/wellness-card/` внутри списка `ul` секции `wellness-services`. Карточка принимает `title`, `description` и `link: { label, href }`. Ссылки используют принятые в проекте адреса будущих подразделов `/wellness/`; сами подразделы этой страницей не создаются. Секция `guest-journey` выводит только реальные этапы: desktop-сетка из шести колонок автоматически заполняется с тремя смещениями через `nth-child`, на мобильном все этапы доступны в нативной горизонтальной прокрутке с CSS Scroll Snap и с клавиатуры. Галерея использует существующие секцию, Swiper и модальное окно с вариантом оформления `wellness`. Сборка создаёт статический `dist/wellness.html`.

`/activity-detail.html` — деталка «Деловые мероприятия» здравницы по макетам 1366 и 360. Данные находятся в `src/data/pages/activity-detail.json`. Страница использует общие баннер, шапку, футер, услуги (`variant: "additional"`, вкладки категорий на мобильном) и галерею (`variant: "activity"`). Ссылка «Подробнее» у деловых мероприятий в `/activities.html` ведёт на деталку. Кнопки «Оставить заявку» на деталке пока не подключены к модалке; «Подробнее» у зала «Южный-1» ведёт на `/hall.html`; остальные залы пока ожидают своих страниц. Для зала можно задать `href`, и кнопка станет ссылкой.

Контент для Битрикса выводится внутри `.editor-content` (`src/components/editor-content/`): `h2`–`h4`, `p`, `ul`, `ol`, `li`, `figure`, `img`, `picture`, `video` и `blockquote` не требуют классов. Необязательный обычный `header` объединяет вводные заголовок и абзац. Отступы задаются через `margin-top` у типов элементов, без sibling-селекторов. Стили обычных тегов ограничены непосредственными детьми контейнера и не затрагивают внутреннюю разметку сниппетов. Первый элемент не имеет верхнего отступа. Межсекционный ритм задаётся через `margin-bottom`.

Для единого поля визуального редактора передайте доверенный HTML в `content.html`, включая HTML сниппетов: он будет выведен без дополнительных обёрток. В статическом примере `content.blocks` показывает чередование фрагментов `html`, `image`, `venues` и `contacts`; это способ сборки примера, а не обязательная структура для админки. В Битриксе можно заменить этот цикл выводом подготовленного детального текста внутри того же `.editor-content`. Пользовательский непроверенный HTML так выводить нельзя.

Сниппеты `eventVenues` (`src/components/event-venues/`) и `eventContacts` (`src/components/event-contacts/`) имеют собственные БЭМ-классы и SCSS. Их итоговую HTML-разметку из `dist/activity-detail.html` можно зарегистрировать как сниппеты визуального редактора Битрикса; текст, количество карточек и контактов редактируются внутри. Контакты `5555` и `4444` — внутренние номера из макета, без ссылки `tel:`. Сборка остаётся статической: `dist/activity-detail.html`, общие CSS, JavaScript и локальные изображения.

`/hall.html` — страница киноконцертного зала «Южный-1» по макетам 1366 и 360. Данные находятся в `src/data/pages/hall.json`. Страницы зала и мероприятия используют общий шаблон `src/templates/activity-detail.njk`, секции `activity-facts` и `activity-content`, шапку, футер, услуги и галерею. `content.variant: "hall"` задаёт отступы страницы зала; `services.showDesktopTabs` включает категории услуг также на десктопе.

Новые сниппеты `eventSeating`, `eventEquipment`, `eventMedia` и `eventAction` лежат в соответствующих папках `src/components/`, каждый со своим SCSS. Они доступны внутри `editorContent` через блоки `seating`, `equipment`, `media` и `action`, либо как готовая HTML-разметка внутри `content.html` при переносе в редактор Битрикса. Рассадка выводится таблицей на десктопе и компактными строками на мобильном; SVG-схемы экспортированы из Figma в `public/assets/hall/` и подключены через общий спрайт и `icon`. Фотографии переиспользуются из проекта; они заполняют контейнер через `object-fit: cover` без геометрических подгонок.

Слайдер фотографий поддерживает стрелки, клавиатуру и свайп. Обе кнопки заявки открывают существующую форму с маской телефона и проверкой обязательных полей; название зала передаётся в скрытом `venue_title`. Для рабочей отправки задайте `request.form.action` либо подключите обработчик Битрикса; демонстрационная отправка не добавлена. Галерея и категории услуг используют существующие механизмы. Сборка создаёт статический `dist/hall.html`.

`/search.html` — пустая страница поиска по десктопному и мобильному макетам. Данные находятся в `src/data/pages/search.json`, секция — в `src/sections/search/`, общая форма — в `src/components/search-form/`. Форма нативно отправляет GET-параметр `q` на `/search-results.html`; адрес, метод, имя параметра, значение и подписи задаются в `search.form`. Клиентский код восстанавливает запрос из URL. При подключении Битрикс замените адрес обработчика и передавайте текущий запрос в `value`. Общие шапка и футер переиспользуются. Сборка создаёт `dist/search.html`.

`/search-results.html` — поисковая выдача по макетам 1366 и 360. Использует ту же секцию поиска с вариантом `results` и тот же БЭМ-компонент `search-form`. Данные — `src/data/pages/search-results.json`, секция — `src/sections/search-results/`. `searchResults.items` содержит заголовки, описания, категории и ссылки; каждая карточка `search-result-card` целиком является одной ссылкой, а «Подробнее» — вложенный неинтерактивный `span` общего компонента `button`. Пока деталки из макета не созданы, ссылки ведут на существующие каталоги соответствующих разделов. Категории `search-categories` фильтруют статические карточки, сохраняют параметр `category` и запрос в URL, поддерживают историю браузера и пустое состояние. Счётчики оставлены по макету и передаются отдельно в `categories.items[].count`. Для Битрикс заполните выдачу, счётчики и реальные адреса из серверного поиска; текущие четыре карточки — статическое наполнение, поиск по содержимому сайта не выполняется. Сборка создаёт `dist/search-results.html`.

Vite собирает отдельные HTML-страницы, TypeScript и SCSS. Nunjucks даёт страницам наследовать общий layout через `extends` и переопределять его блоки. Шрифт Inter поставляется локально через Fontsource и входит в сборку без запросов к Google Fonts. Результат — статические файлы, которые можно подготовить к переносу в сайты Битрикс24.

## Запуск

```bash
npm install
npm run dev
```

Откройте адрес, который выведет Vite. Готовую сборку создаёт `npm run build` в папке `dist/`. Для её локального просмотра — `npm run preview`.

## Структура

- `index.html` — главная страница.
- `about/index.html` — пример внутренней страницы.
- `src/templates/layout.njk` — общий HTML-каркас с блоком `content`.
- `src/components/` — переиспользуемые БЭМ-компоненты; у каждого свой `.njk` и `.scss`.
- `src/sections/` — секции страниц как самостоятельные БЭМ-блоки; у каждой свой `.njk` и `.scss`.
- `src/data/site.json` — общие данные сайта; `src/data/pages/` — данные отдельных страниц.
- `src/styles/main.scss` — точка подключения SCSS компонентов и секций; `_base.scss` и `_tokens.scss` — базовые стили и переменные.
- `src/main.ts` — клиентский TypeScript.
- `vite.config.mjs` — поиск HTML-страниц, подключение шаблонов и загрузка JSON-данных.
- `AGENTS.md` — правила вёрстки, включая `1rem = 10px` и медиавыражения в пикселях.

## Новая страница

Создайте `contacts.html` в корне проекта рядом с `index.html` с наследованием layout и подключением секции:

```html
{% extends "layout.njk" %}
{% block content %}
  {% include "sections/contacts/contacts.njk" %}
{% endblock %}
```

Создайте данные `src/data/pages/contacts.json` с `title`, `description`, `activePage` и данными секции. Добавьте секцию в `src/sections/contacts/` с файлами `contacts.njk` и `_contacts.scss`; подключите SCSS в `src/styles/main.scss`. Для ссылки в навигации дополните `src/data/site.json`.

Страница будет доступна по `/contacts.html` и автоматически попадёт в `dist/contacts.html`. Путь к JSON повторяет путь к HTML-странице внутри `src/data/pages/`.

Файлы из `public/` (если папка нужна) Vite копирует в сборку без обработки. Импортируемые из TypeScript и SCSS ресурсы Vite обрабатывает и хеширует.

## Страница услуг

`/services.html` — каталог по desktop-макету 1366 и мобильному макету 360. Данные находятся в `src/data/pages/services.json`. В сборке страница доступна в `dist/services.html`.

- `breadcrumbs(items, label)` из `src/components/breadcrumbs/breadcrumbs.njk` — самостоятельный БЭМ-блок хлебных крошек без дополнительных классов секций. Принимает массив `{ label, href? }` и название навигации для `aria-label`. Элемент без `href` обозначает текущую страницу; пустой массив не выводит навигацию. Цвет наследуется от окружения.
- `pageBanner(banner)` из `src/sections/page-banner/page-banner.njk` — самостоятельная верхняя секция. Принимает `id`, `title`, `image`, `imageAlt`, `breadcrumbsLabel`, `breadcrumbs`; хлебные крошки выводит через общий компонент `breadcrumbs`. Необязательный `mobileImage` подключается через `<source>` в `<picture>`. Изображение заполняет всю ширину и высоту секции через `object-fit: cover`, без смещений и параметров геометрии. Шапка накладывается на секцию при наличии `page.banner`.
- `filters(config)` из `src/components/filters/filters.njk` — группы с произвольными названиями и вариантами. У каждой группы есть уникальный `id`, `title`, `options` и `defaultOpen` (по умолчанию `false`). Значения изначально не выбраны. `option.all: true` обозначает вариант «Все»/«Любой», исключающий конкретные варианты внутри своей группы.
- На мобильном одна и та же форма переносится в нативный `dialog`; состояния сохраняются. Прокручивается весь диалог, закрытие доступно кнопкой, по Escape и нажатием на фон. Аккордеоны анимируются через `grid-template-rows: 0fr / 1fr`; закрытое содержимое имеет `inert`.
- После изменения форма отправляет всплывающее событие `filters:change`, `event.detail.values` содержит объект массивов значений по ID групп. Это точка подключения фильтрации каталога в Битрикс24; демонстрационная статическая выдача сама не фильтруется.
- `pagination(config)` из `src/components/pagination/pagination.njk` принимает `baseUrl`, `currentPage`, `totalPages`, `items` (номера и строка `ellipsis`), подписи и имена иконок стрелок в спрайте. Троеточие — ссылка на первую скрытую страницу после предыдущего номера; `ellipsisLabel` задаёт подпись перехода для `aria-label`. Ссылки используют `?page=N`; клиентский код обновляет активный номер, ссылку троеточия и доступность стрелок из URL, сохраняя остальные параметры. Данные выдачи для страниц подключаются в Битрикс24.

Иконки выводятся через макрос `icon(name, className, width, height)` в `src/components/icon/icon.njk` и SVG-спрайт `src/components/icon-sprite/icon-sprite.njk`. В `filters.assets` и `pagination.assets` передаются имена иконок в спрайте, а не пути к файлам. Для иконок `<img>` не используется.

Цветовая схема выбирается `page.theme: "beige"` или `"dark-blue"` через класс на `body`. Новые компоненты используют БЭМ, собственные SCSS рядом с шаблонами и общие локальные ресурсы.

## Типовая страница услуги

`/service.html` — страница тренажерного зала по макетам 1366 и 360. Статическая сборка находится в `dist/service.html`, данные — в `src/data/pages/service.json`.

Для новой услуги создайте `<slug>.html` в корне проекта с `{% extends "service.njk" %}` и соответствующий JSON в `src/data/pages/<slug>.json`. Общий шаблон `src/templates/service.njk` подключает четыре секции:

- `serviceIntro` — заголовок, описание, хлебные крошки и характеристики услуги.
- `serviceHero` — фотография и информационная карточка. `info.fields` содержит подписи и значения; `info.instructor` — дополнительную информацию с пояснением. Необязательный `mobileImage` выводится через `<source>` в `<picture>`.
- `serviceContent` — вводный текст, массив `features` и фотография. У каждого блока оснащения есть `title`, `items`, необязательные `description` и `wide`.
- `relatedServices` — заголовок, ссылка на каталог и карточки общего компонента `service-card`. Необязательные `desktopOnly` / `mobileOnly` учитывают отличающийся состав карточек в двух макетах.

Секции и информационная карточка находятся в потоке. На desktop фоновые фотография и затемнение позиционируются абсолютно, а карточка и отступы контейнера определяют высоту секции. На мобильном фотография занимает отдельный блок, карточка располагается под ней. Минимальные высоты карточек сохраняют пропорции макета и позволяют блокам расти при увеличении текста. Фотографии заполняют контейнер через `object-fit: cover`, без смещений и увеличения изображения.

Хедер общий для всех страниц: без баннера он использует светлую поверхность выбранной темы, поверх фото — инверсное оформление. Цвета задаются CSS-переменными `--header-*`, логотип и иконки подключены к общему SVG-спрайту. Навигация, раскрывающиеся панели и клиентская логика используются без дублирования.

## Детальная страница спецпредложения

`/offer.html` — деталка по макетам 1366 и 360, с формой заявки в нижнем блоке. Данные находятся в `src/data/pages/offer.json`, общий шаблон — `src/templates/offer.njk`. Ссылка на эту деталку добавлена в первую карточку `/offers.html`. Чтобы создать другое предложение, добавьте `<slug>.html` в корне с `{% extends "offer.njk" %}` и соответствующий JSON в `src/data/pages/`.

- `offerIntro` содержит хлебные крошки, здравницу, период действия, заголовок, массив кнопок и фотографию. `actions[].href` задаёт URL бронирования или якорь формы; в демо бронирование открывает письмо на существующий адрес сайта. Иконки «Поделиться» и «Печать» используют общий SVG-спрайт. Поделиться открывает системное меню или копирует ссылку.
- `offerContent.blocks` — последовательность блоков `lead`, `benefits`, `list`, `image`, `html`. Блоки можно добавлять, удалять и переставлять. Тексты растут в потоке, принудительных переносов и фиксированных высот текстовых блоков нет. `html` принимает доверенную разметку редактора CMS; её нужно очищать на сервере перед выводом. Для `image` и верхней фотографии поддерживается `mobileImage` через `<picture>`.
- `offerRequest` содержит ID секции и настройки общего компонента `request-form`: `title`, `description`, `fields`, `hiddenFields`, `consent`, `submitLabel`, `action`. Поля задаются массивом `{ name, type, label, autocomplete, required, minLength, maxLength, pattern }`. В демо оставлено поле Email, как в макете; нижний блок оформлен как заявка по заданию. `offer_id` и `offer_title` передаются скрытыми полями. ID формы/секции должны быть уникальны. Согласие и Email проверяет общий `FormValidator`; без JavaScript работает нативная валидация браузера.
- `relatedOffers.items` использует общий `offer-card` с модификатором `related`. На десктопе — сетка из трёх колонок, до 600px — Swiper со свайпом, клавиатурной навигацией и всеми карточками. При возвращении на десктоп экземпляр Swiper уничтожается, восстанавливая сетку.

Для нативной отправки заполните `offerRequest.form.action` адресом обработчика Битрикс; токен сессии и другие служебные значения можно добавить в `hiddenFields`. Для AJAX-интеграции бэкендер подключает собственный обычный обработчик `submit`. Код проекта отвечает только за валидацию: не отправляет запросы, не блокирует кнопку и не показывает результат отправки. Валидная форма продолжает стандартный `submit`, невалидная блокируется валидатором в фазе захвата. Событие `request-form:submit` и прежняя заготовка отправки удалены. Элемент `[data-request-status]` оставлен для сообщений интеграции.

Сборка создаёт `dist/offer.html` и локальные CSS/JS/изображения, без зависимости от Figma и сервера шаблонов. Для переноса в Битрикс замените Nunjucks-циклы серверными циклами CMS, сохранив БЭМ-классы, имена полей и `data-*` атрибуты. Скрипты и стили можно подключать из статической сборки.



## Валидатор форм и интеграция с Битрикс

Класс `FormValidator` экспортируется из `src/utils/form-validator.ts`; `request-form.ts` автоматически подключает его ко всем `.request-form__form` и предоставляет `window.FormValidator` для обычных скриптов Битрикс. Подключайте скрипт интеграции после выполнения основного JS-модуля сайта (например, следующим `type="module"`-скриптом). Для динамически вставленной формы вызовите `new window.FormValidator(form)`.

```js
const form = document.querySelector('.request-form__form');
const validator = window.FormValidator.getInstance(form);

validator.validate();                    // boolean; ошибки и фокус первого неверного поля
validator.validate({ focus: false });    // проверка без перевода фокуса
validator.validateField(form.elements.namedItem('email'));
validator.setErrors({ email: 'Этот email уже подписан.' }); // ошибки сервера по name
validator.reset();                       // убрать ошибки, сохранить значения; ждать новой отправки
form.reset();                            // нативный сброс значений также убирает ошибки
// validator.destroy();                  // снять обработчики и восстановить noValidate
```

`validate()` нужно вызывать перед AJAX, если отправка запускается напрямую, вне события `submit`. Нативный `form.submit()` обходит обработчики и валидацию; `form.requestSubmit()` запускает проверку. Для полностью ручного подключения создайте экземпляр с `{ validateOnSubmit: false }`; существующий экземпляр предварительно отключите через `destroy()`. Валидатор учитывает `formnovalidate` у кнопки отправки.

Правила задаются HTML-атрибутами: `required`, `type="email"`, `pattern`, `minlength`, `maxlength`, а также нативными ограничениями числовых полей и дат. Обязательный текст из одних пробелов не принимается; выключенные и скрытые поля не проверяются. `type="tel"` сам по себе не проверяет формат — задайте `pattern`. Поля `input`, `select`, `textarea` читаются заново при каждой проверке, поэтому динамически добавленные поля тоже работают.

Сообщения находятся в `src/data/site.json` → `formValidation` и передаются в `data-validation-*` на форме. На отдельном поле можно переопределить сообщение тем же атрибутом, например `data-validation-required` или `data-validation-pattern`. Ошибку выводит элемент внутри формы с `data-validation-error-for="имя поля"`; при изменении `name` в Битрикс меняйте этот атрибут соответственно. Валидатор использует `textContent`, `aria-invalid` и `aria-describedby`; подсказки для чтения с экрана сохраняются. Автоматическая проверка начинается только после первой попытки отправки (или вызова `validate()` / `setErrors()` интеграцией), затем ошибки обновляются при вводе, изменении значения и уходе из текстового поля. Чекбоксы и радиокнопки проверяются при изменении значения, без проверки при уходе фокуса. `reset()` и сброс формы снова отключают автоматическую проверку до следующей отправки. Серверная ошибка сохраняется до редактирования поля или сброса ошибок. Общую ошибку отправки интеграция выводит отдельно в `[data-request-status]`. Проверку на сервере реализует Битрикс.

## Цветовые схемы

Схема задаётся полем `theme` в JSON страницы и классом на `body`, который выводит `src/templates/layout.njk`:

```json
{ "theme": "beige" }
```

- `beige` → `body.theme-beige`: существующая палитра основного сайта; используется по умолчанию.
- `dark-blue` → `body.theme-dark-blue`: палитра здравниц из Figma (`2114:1182`, territory/sea). Основной фон светлый `#e9ecf0`, текст `#2d3752`, акцент и фон услуг `#3f4d72`, подвал `#2d3752`. Название темы обозначает палитру, а не тёмный фон всей страницы.

В Битрикс достаточно вывести соответствующий класс на `body`; переключение цветов не требует JavaScript. Главная здравницы создаётся на `/zdravnica.html` с темой `dark-blue`. Пока на ней подключены общая шапка и футер по макету 2332:21950; остальные секции будут добавляться отдельно. Данные находятся в `src/data/pages/zdravnica.json`: `footer.variant: "resort"` задаёт расположение трёх групп ссылок, `footer.navigation` — их наполнение. Контакты и бронирование переиспользуют `src/data/site.json`; подпись бронирования, год копирайта и логотип разработчика заданы на странице по макету. Адреса ещё не созданных разделов размещения и оздоровления указаны как будущие маршруты. Проверить остальные подготовленные блоки можно на существующей главной, заменив в DevTools класс `theme-beige` на `theme-dark-blue`.

Все цветовые значения и обе схемы находятся в `src/styles/_tokens.scss`. Уровни `--theme-50`…`--theme-800` задают палитру; компоненты используют цветовые роли `--color-text-primary`, `--color-text-muted`, `--color-accent`, `--color-page-background`, `--color-surface`, `--color-border` и другие. Для текста поверх фотографий используется `--color-text-inverse`, для светлого текста на цветной поверхности — также `--color-text-inverse-soft`. Нейтральные затемнения фотографий и цвет ошибки общие для обеих схем.

Для секций предусмотрены отдельные роли: `--services-background`, `--special-offers-background`, `--special-offers-color`, `--section-background`, `--footer-background`, `--hero-description-color`. В синей схеме спецпредложения, галерея и новости используют светлый фон страницы; услуги — синий. Декоративные свечения основного сайта отключаются переменной `--services-decoration`. Фоны FAQ и поиска также зависят от темы и сохраняют существующие мобильные варианты.

Добавляя блок, используйте подходящие семантические переменные. Если элементу нужна самостоятельная цветовая роль, добавьте её в общий файл токенов и определите значение для обеих схем. Не вводите hex/RGB-цвета в SCSS компонентов. Палитры и алиасы объявляются на владельце темы, чтобы изменение палитры пересчитывало производные переменные.

Логотипы, фирменные знаки, разделители и иконки выводятся через макрос `icon` и SVG-спрайт с CSS-переменными; геометрия взята из существующих SVG. Поля `header.assets.logo*`, `hero.brandMark*`, `hero.divider*` содержат имена символов спрайта. Цветные метки категорий здравниц (`--color-resort-label-sea`, `--color-resort-label-mountains`, `--color-resort-label-camp`) сохраняют собственные цвета категорий; значения в данных передаются как `var(...)`. Календарь наследует тему через переменные `--calendar-*` и адаптер `--adp-*`.

## Путевки

`/vouchers.html` — страница путевок по макетам 1366 и 360. Данные находятся в `src/data/pages/vouchers.json`, секция — в `src/sections/vouchers/`, компоненты — в `src/components/voucher-card/` и `src/components/booking-modal/`. Общие шапка, футер, баннер, SVG-иконки, диалог и форма переиспользуются. Ссылки «Путевки» в навигации здравницы ведут на новую страницу.

`vouchers.items` задаёт заголовки, описания и начальное состояние аккордеонов. Все путевки изначально свёрнуты. Общие `services` и `photos` воспроизводят наполнение раскрытого примера; для каждой путевки их можно переопределить в соответствующем элементе `items`. Содержимое анимируется через `grid-template-rows: 0fr / 1fr` за 0,6 секунды, закрытая панель получает `inert`. Кнопка «Виды программ Здоровье» раскрывает состав программы и прокручивает к нему.

Кнопки бронирования и «Подробнее» открывают общий попап с содержимым из `bookingModal`, включая заголовок процедуры из предоставленного макета. Выбранные путевка и услуга передаются в скрытых полях `voucher_title` и `service_title`. На мобильном прокручивается весь диалог вместе с кнопкой закрытия; поддерживаются Escape, нажатие на фон, блокировка прокрутки страницы и возврат фокуса.

`bookingModal.form` использует общий `request-form` с вариантом `booking` и `FormValidator`. Поля с `mask` подключают IMask: шаблон показывается по фокусу (в том числе с клавиатуры), у пустого поля после выхода снова видна подпись; незаполненные символы маски удаляются перед отправкой. Форматы: телефон форматируется как +7 (999) 123-45-67 (вставленный номер с 8 нормализуется), время — ЧЧ:ММ, дата — ДД.ММ.ГГГГ. До первой попытки отправки ошибки не показываются; после неё обновляются при вводе, изменении и выходе из поля. Проверяются полное заполнение телефона, допустимое время, существование даты (включая високосные годы) и имя без цифр. Параметры `inputMode` и `errorMessage` задают клавиатуру и подсказки полей. Обязательны имя, телефон и согласие; необязательные время и дата проверяются в форматах ЧЧ:ММ и ДД.ММ.ГГГГ. Отправка следует общей схеме проекта: задайте `action` обработчика Битрикс либо подключите собственный `submit`; демонстрационная отправка и ложное сообщение об успехе не добавлены. Фото баннера заполняет контейнер через `object-fit: cover` без увеличения и смещений, согласно правилам проекта. Сборка создаёт статический `dist/vouchers.html`.

На мобильных экранах крестики закрытия прокручиваются вместе с диалогами. В общем `modal` прокрутка находится на самом диалоге, а не на `modal__content`; в `resort-navigation` панель также находится в общем потоке без собственной прокрутки. Фильтры уже используют эту схему. Крестики не фиксируются поверх содержимого при прокрутке.

## Готовые комплексы услуг

`/programs.html` — каталог программ здравницы по макетам 1366 и 360. Данные — `src/data/pages/programs.json`, секция — `src/sections/program-catalog/`. Страница переиспользует `pageBanner`, шапку и подвал здравницы, общий `catalogLayout` с липкой колонкой и компонент `filters` с мобильным диалогом.

Пятый необязательный аргумент `catalogLayout(navigation, className, label, variant, filterConfig)` заменяет навигацию в колонке на фильтры. Поле `checked` у опции фильтра задаёт начальное состояние. Прежние вызовы макросов работают без изменений.

Переиспользуемый макрос `programCard(card)` находится в `src/components/program-card/`. Карточка получает `title`, `description`, `tags`, `link`, необязательный `wideDescription`, а для фильтрации — `minDays` и `types`. Длительность означает доступный срок пребывания: программа с `minDays: 6` подходит для выбора 7 и 14 дней. Внутри группы варианты объединяются по ИЛИ, между группами — по И. Все десять карточек, включая повтор «Снижение веса», сохранены по макету.

Ссылки на каталог в навигации здравниц и на странице оздоровления ведут на `/programs.html`. Кнопка «Подробнее» программы «Здоровье Плюс» ведёт на `/program.html`; остальные адреса заданы в JSON как будущие маршруты `/wellness/programs/<slug>/`. Фото баннера из Figma хранится локально и заполняет контейнер через `object-fit: cover` без смещений. Результат сборки — статический `dist/programs.html`.

`/program.html` — страница программы «Здоровье +» по макетам 1366 и 360. Данные — `src/data/pages/program.json`, фотографии — `public/assets/program/`. Первый экран переиспользует `hero` с `detailVariant: "program"`, форму бронирования, хлебные крошки и SVG-знак из общего спрайта. Поле `hero.textLines` позволяет сохранить переносы вводного текста из макета.

Секции страницы находятся в `program-overview`, `program-path`, `program-indications` и `related-programs`. Карточки пути используют компонент `programBenefit`: на десктопе — CSS columns со смещением второй колонки, на мобильном — последовательная раскладка. «Другие программы» переиспользует `programCard` внутри Swiper со стрелками, перетаскиванием и клавиатурной навигацией. На десктопе изначально выбрана средняя карточка, на мобильном — первая. Сборка создаёт статический `dist/program.html`.
